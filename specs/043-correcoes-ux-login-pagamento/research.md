# Research: Três Correções de UX

Decisões técnicas da Phase 0. Não havia "NEEDS CLARIFICATION" pendente no Technical Context — a spec já resolveu os 3 itens via investigação de código antes de ser escrita.

## R1. Login — Enter já funciona; a lacuna real é duplo-envio

- **Decision**: nenhuma mudança na ligação `<form onSubmit>`/`<button type="submit">` de `LoginForm.tsx` — já está correta. A única mudança de código é uma guarda no topo de `handleSubmit`: `if (carregando) return;` antes de qualquer outra coisa, cobrindo tanto Enter repetido quanto clique duplo.
- **Rationale**: leitura do código (spec.md, Nota de investigação prévia) não encontrou nenhum bloqueio ao Enter. Confirmar isso num navegador real (research.md R-validação, quickstart §1) é mais barato e mais confiável do que reescrever um comportamento que já existe. A guarda contra duplo-envio é uma lacuna de verdade, independente do gatilho (Enter ou clique): hoje só o botão fica `disabled` durante o envio, mas um Enter disparado direto no campo não passa pelo botão.
- **Alternatives considered**: adicionar um `onKeyDown` customizado nos campos para "forçar" o submit no Enter — descartado, já é o comportamento nativo do HTML e adicionar um handler customizado só aumentaria a chance de regressão (ex.: capturar Enter duas vezes, uma do nativo e uma do handler).

## R2. Recuperação de senha — configuração via User Secrets, validação com envio real

- **Decision**: `dotnet user-secrets set "Brevo:SmtpUsuario" "<login>" --project src/SPI.Api`, idem para `Brevo:SmtpChave` e `Brevo:RemetenteEmail`, usando as credenciais reais fornecidas temporariamente durante a implementação (nunca em `appsettings.json`/`appsettings.Development.json`, nunca commitadas). Depois de configurado, subir o backend e chamar `POST /api/auth/esqueci-senha` de verdade para uma conta de teste cadastrada, confirmando o recebimento real do e-mail.
- **Rationale**: o código de envio (`BrevoEmailSender`, MailKit/SMTP) já está correto — o único "bug" confirmado é a ausência de configuração. `dotnet user-secrets` é o mecanismo já padronizado no projeto (mesmo usado para `Jwt:Key`/`ConnectionStrings:SpiDB`), e testar via o endpoint real (em vez de um script solto chamando o MailKit direto) prova o fluxo de ponta a ponta de verdade: validação → geração de token → envio → resposta idêntica para e-mail existente/inexistente (FR-003).
- **Alternatives considered**: um script solto de smoke test (MailKit/`Send-MailMessage` direto, sem subir o backend) — mais rápido, mas só prova que a Brevo aceita as credenciais, não que o fluxo real do `RecuperacaoSenhaService` (geração de token, FR-003) funciona de ponta a ponta. Reservado como plano B se subir o backend completo não for viável no momento da implementação.
- **Credenciais**: a professora já forneceu os 3 valores (SMTP login, SMTP key, e-mail remetente) numa conversa anterior a este plano, mas a regra de não-persistência já em uso nesta sessão (descartar ao final, nunca guardar em memória entre tarefas) significa que eles MUST ser solicitados de novo no momento da implementação, não reaproveitados desta conversa. **Diferença em relação às credenciais do Trello (specs/040-042)**: aquelas eram só para validação pontual de uma ferramenta de processo e foram descartadas de propósito; estas 3 chaves da Brevo são a configuração real e contínua da capacidade de recuperação de senha do produto — por isso ficam persistidas em User Secrets (mesmo tratamento de `Jwt:Key`/`ConnectionStrings:SpiDB`), não removidas ao final da implementação.
- **Achado real na implementação (T003/T004)**: com as credenciais configuradas, `POST /api/auth/esqueci-senha` devolveu `200` com a mensagem genérica correta e o erro foi logado (FR-003/FR-004 confirmados), mas o e-mail não chegou — `MailKit.Net.Smtp.SmtpClient.ConnectAsync` expirou em 120s dentro do handshake com `smtp-relay.brevo.com:587`. Um teste de TCP bruto (`Test-NetConnection` + leitura manual do banner SMTP) isolou a causa com mais precisão do que "porta bloqueada": a mesma ausência de banner se repete nas portas 587, 2525 **e** 465 contra a Brevo, enquanto **SMTP para `smtp.gmail.com:587` funciona normalmente** (banner `220` chega na hora) e **HTTPS para o próprio host da Brevo (porta 443) também funciona**. Ou seja, não é bloqueio de porta nem de host/IP em geral — é tráfego SMTP especificamente destinado à Brevo sendo silenciosamente descartado, o padrão típico de um antivírus/firewall local com heurística de reputação contra relays de e-mail em massa (Brevo/SendinBlue é um alvo comum desse tipo de regra). Nenhuma mudança de código foi feita ou é indicada — `BrevoEmailSender.cs`/`RecuperacaoSenhaService.cs` continuam corretos, e trocar de porta não resolveria (testado e descartado). Decisão do usuário: documentar como limitação de ambiente conhecida e seguir em frente — a confirmação real de entrega (SC-001) fica pendente de um ambiente sem esse bloqueio (ex.: onde o backend for hospedado de verdade).

## R3. Botões de status — separar exibição (StatusPill) de ação (ConfirmModal), reaproveitando componentes existentes

- **Decision**: a seção "Alterar status" das duas telas (`contas-a-pagar/[id]`, `contas-a-receber/[id]`) passa a mostrar:
  1. O status atual como um `StatusPill` (componente já existente, usado em outras telas para exibir status — nunca clicável, só informativo).
  2. Só os **outros 3** valores como botões de ação, com rótulo de verbo ("Marcar como Pago", "Marcar como Atrasado", "Cancelar conta" — não mais o nome nu do status).
  3. Clicar em qualquer um abre o `ConfirmModal` já existente (mesmo componente usado em excluir aluno/cancelar aula), com `titulo`/`descricao` específicos da transição (reaproveitando o texto de aviso que já existe hoje, mas movido para dentro da confirmação) e `confirmVariant="btn-primary"` (não é uma ação destrutiva no sentido de excluir dado, então não usa `btn-danger`, exceto possivelmente para "Cancelado" — decisão de polimento visual, não funcional).
  4. Só ao confirmar, `handleStatus` é chamado (mesma função/endpoint de hoje).
- **Rationale**: a causa raiz do "parece filtro" é mostrar o status atual e as opções de transição misturados na mesma fileira de botões, com o mesmo componente visual (`btn-primary`/`btn-ghost`) usado em outros lugares do sistema para alternar filtro de exibição (ex.: filtro de Ativo/Inativo em listagens). Separar "o que é" (pill, não clicável) de "o que posso fazer" (botões de ação, com verbo) resolve a ambiguidade sem inventar nenhum componente novo. Reaproveitar `ConfirmModal` evita duplicar lógica de modal de confirmação (já existe, já é usado, já segue o padrão visual do projeto).
- **Alternatives considered**: só mudar a cor/ícone dos botões sem modal — rejeitado, não cobre FR-005 (exigência de confirmação explícita) sozinho; um componente de modal novo, dedicado a status — descartado, `ConfirmModal` já é genérico o bastante (recebe `titulo`/`descricao`/callbacks).

## R4. Validação sem suíte automatizada de frontend

- **Decision**: validação manual no navegador (`quickstart.md`) para os itens 1 e 3; validação com envio real de e-mail (R2) para o item 2. Mesma decisão já aceita neste projeto para mudanças de frontend (o projeto não tem testes de UI automatizados hoje).
- **Rationale**: consistente com a prática já estabelecida (specs 037-042 sempre trataram validação de frontend/scripts como manual, reservando testes automatizados para `SPI.Application.Tests`, camada de serviço do backend).
